## 1. 交付目标与边界

用户描述一个仓库没有预设、但能用现有机制表达的纸牌玩法，系统完成：

```text
自然语言 → 规则草案与歧义澄清 → 机制能力检查
        → 组合规则 → 宿主编译 GamePlan → 独立验证
        → 用户核对规则 → 注册不可变玩法版本 → 浏览器与电脑完整试玩
```

本阶段成功的关键：**增加一个玩法时，不必增加一个 IR 家族、Python 计划函数、专属工具、机器人分支或前端玩法分支。**

“陌生”指仓库没有该玩法的专门实现，不要求模型从未听过它。能生成的范围由宿主已经实现且验证过的机制子集决定。

### 1.1 纳入范围

- 本机单用户，1 个真人座位，其他座位由确定性机器人操作；新组合优先支持 2～4 人顺序行动。
- 牌堆、牌区、公开/本人可见/完全隐藏、发牌与移动、单牌/有限多牌选择。
- 已有机制中经过复核的比较、同点组合、同花/同点匹配、计分、回合推进、有限特殊牌效果。
- 与预设玩法不同的阶段顺序、动作选择、计分及终局组合。
- 持久化设计会话、局部规则修复、完整验证报告、规则核对、注册及对局恢复。
- 局部声明式宏复用；宏展开仍进入同一个 Interpreter。

### 1.2 不在本阶段承诺的能力

- 任意自然语言规则、任意数学表达式、无限状态机或任意代码生成。
- 同时行动、实时抢牌、网络多人、账号权限体系、外挂服务、沙箱代码执行。
- 通用反应栈、无限递归触发、耐心游戏自动布局、未复核的完整桥牌/斗地主/德州扑克。
- 自动证明游戏平衡、有趣，或证明自然语言与 IR 完全等价。
- 全功能视频式回放、动画重设计、离线导出。

不能表达的规则返回具体 `unsupported`；验证资源不足返回 `verification_inconclusive`；编译器自身错误返回 `compiler_error`。三者不得混为一谈，也不自动改成近似玩法。

### 2.3 真正阻塞 G2 的缺口

1. **规则入口封闭**：`RulesIR` 是固定 8 类判别联合，不能直接描述新的机制组合。
2. **操作不够正交**：`MatchingTool.play` 自带空手终局，`TrickTool.play` 自带计分/终局，`HiddenDrawTool.ask` 绑定取牌失败后的摸牌策略；新的规则难以独立重组。
3. **能力粒度过粗**：`turn_adapter` 标成 stable 不等于已实现竞叫或优先权；`hidden_draw.ask` 不等于支持按隐藏位置抽牌。语料库标签覆盖不能当作可运行覆盖。
4. **发现信息不足**：元工具没有完整的机制/operation/config schema 查询；参数多为名称列表，返回类型多为自由文本。`binding.name` 同时作为工具类型和实例键，不能自然表达同工具不同配置的两个实例。
5. **门槛未绑定产物**：`finalize` 主要信任 report.ok；缺少 IR、能力检查、Plan、验证策略和版本之间的强制绑定；没有实际的完整 `contract_check`。
6. **动作协议固定**：API 只接 `card_index/expression/declared_suit/amount`；前端与机器人按动作名识别，无法支持“选两张牌再选一个目标区域”等输入。
7. **设计状态不持久**：每次 run_loop 都新建 LoopState；跨 HTTP 澄清仅保留聊天文字，不能可靠保留 IR、草案和验证结果。
8. **运行投影固定**：view 基于 hands/table 等约定，且事件只返回最近 100 条。G2 的多牌区、私密动作参数和完整验证轨迹需要明确协议。

## 3. 核心架构决策

### 3.1 Agent 组装规则，宿主完成低层编译

G2 默认采用 **ComposedRulesIR + 确定性降层**：Agent 选择已有机制、声明动作和阶段顺序；编译器把组合规则转成 GamePlan。

```text
                          ┌─ KnownRulesIR → 现有 host_compile ─┐
自然语言 → 设计服务/Agent ─┤                                 ├→ GamePlan
                          └─ ComposedRulesIR → 通用编译器 ────┘
                                                              ↓
                                              同一验证服务 / 同一 Interpreter
```

两种编译入口是输入格式差异，不是两套执行器。一个玩法版本只能绑定一份 IR、一份编译产物和一个编译来源，运行时不得自动选择另一份计划。

不要求模型手工拼接每一个 `call/branch/wait` 节点，也不向模型注入某个验收玩法的完整模板。模型组合的对象是受约束的机制声明，宿主只为操作类型写编译规则，不按游戏标题或 ID 分派。

公开设计路径移除 `compose_plan(plan=<任意 JSON>)` 的直接发布能力。原始 Plan 仅可用于开发验证、导入审查或故障注入；不能绕过组合 IR 与同一验证服务进入游戏库。

这个决定对 v0.4 文档中“Agent 直接产候选 Plan”作收窄，实施前以 ADR 记录；目的在于减少第二份手写语义，保留既有 Interpreter。

### 3.2 同一能力目录约束模型与宿主

机制目录从已注册的 operation、配置 Schema、参数范围、读写集和验证器生成，向 Agent 提供同源信息。

能力检查分两层：

- 预检：从 IR 的类型化语义节点推导需求，如 `selection.cards.count=2`、`turn.sequential.skip`。
- 解析/编译：检查参数、读写依赖、事件时机、可见性、机器人输入生成和 UI 控件是否全部可用。

不能仅用“所需轴全部 stable”决定组合可发布。宏只能展开已有能力，不能填补未实现的 operation。

## 4. 数据契约（目标设计，尚未实现）

### 4.1 ComposedRulesIR

采用一个 `kind: composed`，不随新玩法增加 `Literal[新游戏名]`。版本建议 `0.5`，已知 `0.4` IR 保留兼容解析。

| 字段 | 内容与约束 |
|---|---|
| `meta` | 标题、说明；存储 ID 由宿主分配；标题不影响编译路径 |
| `requirements` | 用户需求条款、原文来源、已表达/待澄清状态、对应规则节点 ID |
| `players` | 人数、座位顺序；G2 新组合限制 2～4 人 |
| `deck` | 唯一 rank/suit、显式牌值、copies；生成稳定且唯一的 card ID |
| `zones` | 有限牌区、owner、顺序、visibility；每张牌只有一个权威所属区 |
| `setup` | 有限初始化与发牌声明 |
| `variables` | 有类型、有初值的用户规则变量，限定在 `game.*` 命名空间 |
| `actions` | actor、guard、输入选择、受约束效果、对应需求条款 |
| `flow` | 有限阶段、当前座位、跳过规则、有限重复及退出条件 |
| `scoring` | 分数产生、转移和结算条件；不默认假定所有计分零和 |
| `terminal` | 正常结束条件、平局、赢家策略和明确的最大回合规则 |
| `macros` | 设计内局部的类型化动作/效果片段；可展开、不可递归 |

表达式只允许类型化 AST：字面量、合法字段引用、整数运算、比较、布尔逻辑、有限集合操作。不接受 `eval`、自由 Python/JS、反射、动态 import、任意状态路径或递归调用。

所有规则条件必须有静态类型；引用的字段必须存在且已初始化。不支持的语义必须作为未解决需求保留，不能塞进 `description` 后忽略。

需求条款仍可能被模型漏译。Schema 和 source map 不能证明自然语言已被完整理解；这部分由用户核对、独立需求预期和“遗漏条款”反例共同检验。

### 4.2 效果与控制流的明确语义

- 先校验 actor、输入、guard，全部合法后再执行动作事务。
- 选择本身无副作用；选中的 card ID 必须属于声明的牌区且对本操作有效。
- 效果按 IR 列表顺序执行；一个逻辑动作及后续机器人响应作为一次 API 提交单位，成功才递增 revision 并保存。
- 计分、结束判定、特殊牌效果、回合推进的先后必须在 IR 中明确，不由工具暗中补齐。
- G2 事件钩子限定为 `after_action`、`after_round`、`before_next_actor`；不做任意事件递归触发。
- 真正的结束条件与运行预算分开：预算耗尽是验证/运行失败，不能伪装成平局或胜利。
- 卡牌移出手牌必须进入另一个牌区；收集区/弃牌区仍计入牌身份守恒。`table` 如只是展示投影，不得再次计作牌区。

### 4.3 机制契约与实例绑定

为可组合 operation 补齐 `config_schema / input_schema / output_schema / reads / writes / requires / ensures / feature_constraints`。用 Pydantic 等现有依赖生成机器可读 Schema。

区分 `binding_id` 和 `tool_type`，允许同一种参数化工具有两个独立配置实例。兼容旧 `name` 的解析只放在入口，Interpreter 内使用一种标准绑定表示。

这会改变 Plan 协议：目标 Plan Schema 同步升为 `0.5`，并为已有 `0.4` 存档提供明确、可测试的兼容/迁移方案。不能改变旧字段含义却继续使用同一 Schema 版本，也不能把迁移后的哈希当成旧验证证据。

保留工具自身的强制校验；模型声明的 requires/ensures 只能收紧约束，不能覆盖宿主契约。`state.update` 的全写集不是组合 IR 的逃生口；组合编译器只生成已声明字段的写入。

### 4.4 GameArtifact 与验证凭据

注册对象升级为不可变 `GameArtifact`：

```text
game_id / version
generation_source = known_parameters | composed_rules
normalized_ir + ir_hash
compiled_plan + plan_hash + source_map
compiler_version / registry_contract_hash / runtime_version
expanded_macro_hashes / ui_schema_version
verification_id / approval_ir_hash
```

`source_map` 将 IR 的动作和需求条款映射到 Plan 节点；编译器生成，模型不能自行宣称映射成功。

`game_id` 是存储身份，`game_kind` 是规则分类，二者不要求字符串相等；一致性通过 IR/Plan 哈希和 artifact 绑定检查，不以名字相同替代。`generation_source` 由实际编译路径记录，不能由模型自报。

`VerificationResult` 由宿主保存，并绑定以上哈希、策略版本、种子列表、覆盖项及结论。发布接口接受 `verification_id`，不能接受调用方传来的 `{ok: true}` 作为证据。诊断模拟可用自选 seed；正式门禁的种子、策略和不变量由宿主决定。

IR、宏、编译器或工具契约变化后，旧验证凭据不能批准新产物。同一玩法新规则创建新版本，不能覆盖旧版本；已存在的内置 ID 保护继续保留。检查和写入必须在同一 SQLite 事务中，并有唯一键约束。

### 4.5 通用动作与视图

新增版本化动作描述：

```json
{
  "id": "exchange",
  "label": "交换一张牌",
  "actor": "player-1",
  "inputs": [
    {"id": "from_hand", "kind": "card_selection", "zone_id": "hand-1", "min": 1, "max": 1},
    {"id": "from_market", "kind": "card_selection", "zone_id": "market", "min": 1, "max": 1}
  ]
}
```

这是形状示例，完整 Schema 在 M1 冻结。选择器还需携带有限候选、依赖关系和约束；金额提供 min/max/step，枚举提供合法值。较大候选空间由服务端按有界查询生成，不能一次无限枚举。

新动作请求：`{revision, action_id, input_values, request_id}`。actor 由本地 session 的受控座位决定，不信任客户端自由声明。当前单用户不引入账号系统；viewer 切换仅用于受控开发测试，不能让普通 API 任意读取对手牌。

通用 view 至少包含：`players / teams / zones / actions / turn / scores / phase / result / revision / event_cursor`。状态、事件和错误都经过同一玩家视角投影；隐藏牌不得通过候选列表、card ID、事件参数或错误细节泄露。

机器人使用当前座位的可见视图和相同动作 Schema 生成合法输入，不按 `game_kind` 写策略，不探测隐藏状态后决定行动。无可生成输入是明确缺口，不退化为默认 `card_index=0`。

## 5. 发布状态机与错误分类

```text
draft → needs_clarification / capability_checked
      → compiled → validated → verified → awaiting_confirmation
      → ready → registered
```

- 用户规则确认与技术验证可先后独立完成，但发布时二者必须指向同一 `ir_hash`。
- Agent 可以自动完成组合、诊断和有限修复；不能替用户调用确认接口。
- 每次 IR/宏修订使编译、验证、确认标识失效；只改显示标题是否免重新验证由明确的元数据规则决定。
- 任意 `finalize` 调用都由同一个服务重新检查当前前置条件，不依赖模型是否按提示词调用过某个工具。
- `unsupported`、`validation_failed`、`verification_inconclusive`、`budget_exhausted`、`host_error` 分别记录；超时和内部异常不解释为“这个游戏不可能表达”。
- 已转换的工具异常机制继续保留；内部错误保存日志与 correlation ID，对模型返回可定位摘要。宿主错误不让模型通过偷偷改规则“修复”。

### M0：建立本轮可执行基线

1. 在专用数据目录启动 `3ce565a`，验证已知 8 个玩法的现有入口；重新收集测试/浏览器证据，不复用旧统计当作新结果。
2. 写 ADR：组合 IR 降层、原始 Plan 入口收窄、Schema/数据迁移、证据与版本绑定。

6. 新子目录进入架构扫描：将只扫描 `core/*.py` 的检查扩展到递归路径，避免模块拆分绕过单一执行器检查。

涉及：`docs/adr/`、`docs/engineering-standards.md`、`core/capability.py`、`tests/test_architecture_invariants.py`、能力 corpus。

### M1：把已有行为拆成可组合操作

1. 操作契约补类型化 Schema，消除 `params` 只有名称、返回值只有说明字符串的缺口。
2. 引入稳定牌区引用、唯一牌所属关系、通用选择与移动；复用既有 deck/CardRef，避免新建平行牌堆模型。

4. 回合方向、skip 的消费时机、牌堆耗尽及回收策略由规则显式决定。已有 `trigger.apply` 不能替规则选择隐式回收或终局行为。
5. 定义通用动作 Schema 和输入验证器；给机器人、测试策略与 UI 共用，动作标识不再承担全部参数编码职责。
6. 原有工具若仍需兼容，使用薄适配层调用相同底层机制；每项适配记录迁移消费者和删除所在 PR，不保留第二份行为实现。

涉及：`core/contracts.py`、`registry.py`、`tools.py`、`hidden_tools.py`、`trigger_tools.py`、`plan.py`；新增候选 `core/zones.py`、`core/actions.py`。

准出测试：选牌数量/所有权错误不能改状态；出完手牌但终局是“达到分数”时不得自动结束；重复副本守恒；同一 move/score/turn 操作用于两种不同组合；旧玩法受影响部分真实运行无退化。

### M2：组合规则解析与确定性编译

1. 在 IR 入口新增 composed 判别分支，拆出机制描述、表达式类型、阶段和效果 Schema；解析边界拒绝未知字段和任意代码。
2. 实现 `derive_requirements(ir)`、`resolve_composition(ir, catalog)`；不仅检查 axis 存在，还检查所需变体、参数、牌区、状态读写和交互输入的可用性。
3. 编译器按选择、移动、比较、计分、阶段等语义节点降层；输出 GamePlan 和 source map。编译函数不得按新游戏 ID、标题或固定完整描述匹配。
4. 检查初始化/引用类型、控制流引用、展开后规模、入口可达性和无等待环。有限循环必须显式有界；复杂可达性超预算返回待验证，不能宣称一般图终止已证明。
5. 同一规范化 IR + 编译器版本 + 机制目录版本生成相同的 Plan/hash。编译错误返回 IR 路径和条款 ID。
6. 完成场景 A 的“人工规则数据 → 编译 → 真实 API 模拟”垂直切片；此时是开发草案，直到 M3 通过门槛才提供正式试玩入口。

涉及：`core/ir.py` 拆分；候选 `core/rules/`、`core/compiler/`；更新 `core/macros.py`、`capability.py`。拆分必须搬迁原实现与更新引用，不复制已知族实现到新目录。

### M3：验证证据与不可绕过的门禁

1. 实现发布服务：输入设计 revision，依次检查规范化 IR、能力解析、编译产物、动态验证、规则确认，产生不可变 artifact。
2. `contract_check` 从宿主支持的条款类型生成监测器，检查动作选择、移动效果、分数、阶段、结束原因与赢家；不能只检查 trace 是否打印了条款文本。
3. 记录实际动作输入和逐步状态摘要，按相同输入日志重放，而非只重新跑一次同策略；对规范化事件与状态分别比较。
4. 正式 playtest 至少使用合法随机、边界、目标分支三种策略；目标分支策略是本包新增，当前代码尚无该策略。策略生成动作参数，以固定 seed 保持复现。验收游戏不允许靠不断 give_up/fold 通过。
5. 全部等待点、用户动作类型、关键触发器、计分分支和终局分支须有证据。未覆盖但预期可达的关键分支不可发布；通过有界分析证明不可能的分支需宿主给出说明，模型不能豁免。
6. 增加类型化不变量：牌身份/区域守恒、资源守恒或合法产生消耗、得分边界、失败原子性、视角安全；每步及 setup/终局检查。
7. 做变异测试：故意改倍率、赢家、轮数、可见性、触发顺序，验证独立监测器能拒绝。不能由同一编译函数同时产出实现和“独立答案”。
8. verification_id 绑定 IR/Plan/机制版本/策略；注册验证与数据库写入原子化；会话按不可变版本恢复。没有运行版本可恢复时明确报错，不自动改用新计划。
9. 将 human step + bots + 保存视为整体提交。内存与 SQLite 模式都验证机器人失败时不会留下已推进但 revision 未增的状态；request_id 支持重复提交去重。

涉及：候选 `core/verify/`、`core/artifacts.py`；更新 `playtest.py`、`policy.py`、`session.py`、`app.py`。

### M4：让 Agent 真正组合与修复

新增/收敛元工具，全部经同一设计服务：

| 元工具 | 作用 |
|---|---|
| `list_capabilities` / `describe_mechanism` | 查询操作、参数、限制和缺口；同源于注册表 |
| `propose_ir` / `patch_ir` | 提交或按 revision 修订组合规则 |
| `capability_check` | 返回机制变体与组合依赖缺口 |
| `define_local_macro` / `validate_macro` | 建立设计内局部片段；限制展开量与调用深度 |
| `compose_plan` | 对当前 IR revision 编译，不接受模型提供任意 raw Plan |
| `validate_plan` / `simulate` / `verify_game` | 快速诊断与正式验证分开 |
| `inspect_failure` | 返回失败路径、相关条款、动作输入、精简状态差异 |
| `finalize` | 尝试冻结技术产物；只由宿主判断当前证据是否满足 |
| `ask_user` / `unsupported` | 处理未解决需求与能力缺口 |

1. 持久化 `DesignSession`：聊天、需求条款、IR、宏、revision、编译产物、验证 ID、当前状态、已用预算。
2. 每次请求先恢复状态，改动使用乐观并发；模型工具观察不作为下一次请求的唯一状态来源。
3. 局部修复只改相应 IR/宏片段，再重新编译与验证；不得为通过测试删除用户条款。未改变需求时，复用已经确认的需求来源；行为语义变化需要重新核对。
4. 宏参数使用有类型占位节点，替换当前字符串插值不能承载对象/数字类型的问题；使用明确局部变量与引用规则，避免展开冲突。G2 只允许有限、无递归的局部宏，不自动把模型片段提升为 Python tool。
5. JSON 决策协议可以保留；标准 function calling 作为可选传输适配，不作为 G2 的必要前置。
6. 限制总模型步数、token、墙钟时间、单步输出与修复次数。可恢复异常回灌；宿主错误记录日志并停止该轮，不无上限请求模型修宿主。
7. Agent 产物是候选规则；用户确认来自独立 UI/API，不接受 Agent 元工具自确认。

涉及：`agent/loop.py`、`meta_tools.py`、候选 `agent/design_service.py`、`agent/design_store.py`、`llm.py` 与 API。

## 7. 初始预算与验证限制

以下是 M0 需根据实际设备基线确认的初始工程上限，变更必须留下理由：

| 项目 | 初始上限 |
|---|---|
| 新组合玩家 / 牌总量 / 牌区数 | 4 / 108 / 24 |
| 用户动作定义 / 单次可选牌数 | 16 / 5 |
| IR AST 深度 / 展开 Plan 节点 | 12 / 512 |
| 局部宏数 / 宏引用层数 | 16 / 3，无递归 |
| 单动作效果次数 / 事件钩子链长度 | 64 / 8 |
| 动作参数候选枚举 | 每次查询 ≤256，超限需有界筛选策略 |
| 单局验证动作数 / 无等待解释步数 | 2048 / 1024 |
| 正式种子 / 策略 | 至少 10 个固定 seed × 3 类策略，边界 fixture 另计 |
| 一轮自动设计预算 | ≤24 次模型决策、≤4 次自动修复、≤48k 累计 token、≤180 秒 |
| 单轮验证运行预算 | 初始 30 秒墙钟、512 MiB 内存；M0 实测后冻结 |

检查点计时不能中止一个卡住的 operation。正式验证需要可终止的受限子进程及平台适配，仍执行同一 Interpreter，不允许模型代码进入其中。超预算保存失败证据并回收资源。

核心工具数量继续遵守当前 18 的预算。优先提取内部纯函数并复用现有注册项；确需增加通用操作/工具时提交 ADR 和至少两个真实消费者，不为保持数字而把不同职责塞进一个全能工具。

## 8. 准出场景与判断标准

### 8.1 三个开发期正例

以下均为人工定义的测试玩法，不声称是某个传统游戏的标准规则。M0 冻结为带独立预期的需求条款，所有歧义必须在进入 Agent 验收前消除。

统一计数：一个“行动回合”是一次当前玩家的 action，出牌、交换、摸牌或 pass 均计一次；被 skip 的座位不计行动。API revision 计成功的真人请求及其机器人响应批次，不能与行动数混用。独立 fixture 应固定初始牌序/seed、动作日志或策略，再断言行动数、轮数及 revision；只有 seed 不能确定玩家决策后的终局。

**场景 A：手牌选择 + 顺序公开比较 + 三轮积分**

- 两人，牌为 2～9、S/H 两花色、单副，数值按牌点；每人发 3 张公开手牌，其余留牌堆。
- 每轮双方依次从手牌选择一张放入公共区；第 1、3 轮 player-1 先，第 2 轮 player-2 先。
- 两张牌较大者得 1 分，相同则无人得分；比较后两张牌进入弃牌区。
- 共 3 轮，最高总分获胜，平分时两人并列；不补牌。
- 每轮包含双方各一次行动，完整对局共 6 次 actor action。
- 验收区别：具有“选择哪张牌”与先手轮换，不能退化为已有 War 的自动各抽一张。

**场景 B：接牌 + 按花色计分 + 跳过 + 自定义结束**

- 两人，牌为 2～9、S/H 两花色、单副；每人 4 张隐藏手牌，发 1 张起始牌到公共弃牌区，其余为牌堆。
- player-1 先手；起始牌不计分、不触发特殊效果，后续匹配目标为弃牌区最新的一张。
- 玩家可出一张同点或同花的牌。出 H 得 2 分、出 S 得 1 分；出 7 在未终局时跳过下家一次。
- 顺序为“移牌 → 加分 → 终局判断 → 特殊效果 → 推进座位”。任何人达到 6 分立即结束；出完手牌本身不结束。
- 无合法牌时摸 1 张并结束本回合，不在同回合再出；无合法牌且牌堆空时 pass。空手也按此规则处理，不回收弃牌。
- 达到 6 分时只结算，不再执行 7 的 skip；摸牌成功和 pass 都各计一个行动回合。
- 若尚无人达 6 分，完成 20 个行动回合后按最高分结束，平分并列；被跳过的座位不额外计入行动回合。
- 验收区别：终局不能来自 matching 工具内置的“空手获胜”；需要证明未被套成固定 UNO。

**场景 C：公开市场交换 + 同点成对移除 + 得分**

- 两人，牌为 2～9、S/H 两花色、单副；各 3 张公开手牌、市场 3 张公开牌，其余为牌堆。
- player-1 先手。交换一入一出，市场始终保持 3 张；手牌、市场、牌堆、收集区合计始终为 16 张。
- setup 时不消除对子。每回合交换恰好 1 张本人手牌与 1 张市场牌，然后从本人手牌移除全部同点对子到收集区，每对加 2 分。
- 对子移除后从牌堆补到 3 张，牌堆不足则补到耗尽；补牌后产生的对子留到该玩家下次交换后处理。
- 无手牌且牌堆仍有牌时先补到 3 张再进入交换；手牌与牌堆都空时 pass。
- 补牌不足 3 张时补到牌堆耗尽。每对由两张同 rank 的牌组成；本牌组每个 rank 最多一对。补牌是本回合的内部效果，不单独计行动；pass 计行动。
- 共 12 个行动回合，最高分获胜，平分并列；不因提前空手自动结束。
- 验收区别：一个动作需要两个区域的选择输入，现有固定 `card_index` 和按游戏名 UI 无法代替。

**正例共同通过条件：**

- 不新增专属 IR 类、`*_plan` 函数、机器人或前端分支。
- 由真实模型根据自然语言产生 composed IR；不能用预写 Plan 注入模型或 API 冒充生成。
- 验收 fixture 只提供独立需求条款/预期结果，不向 Agent 提供答案 IR 或 Plan；开发期人工 IR 模拟不计入真实生成成绩。
- artifact 必须记录 `generation_source=composed_rules`；编译轨迹证明走通用机制编译器，未调用某个内置玩法计划函数。
- 模型自动完成组合/有限修复，用户仅澄清规则及核对产物；不手工改代码或 Plan 救场。
- UI 展示真实条款，确认后注册；同一服务开局，与机器人走到正常结束，再开一局。
- 刷新前后保持同一 session/version/revision；后端重启后恢复，关闭模型可用性后牌局仍能继续。
- 非法选牌/金额/重复请求/过期 revision 可重复触发，失败不会改局面。

### 8.2 反例与门禁测试

| 输入/故障 | 必须观察到的结果 |
|---|---|
| “同时翻牌，最快点击者抢走” | `unsupported: simultaneous/realtime_reaction`，不得改成顺序行动 |
| “卡牌执行任意 Python/访问外部网站” | `unsupported`，没有代码执行入口 |
| 模型把终局赢家写死为自己 | 结构/条款验证失败，不注册 |
| 修改 IR 后复用旧验证 ID | `verification_stale`，要求重新验证 |
| 只提交一个 `ok:true` 的报告 | 拒绝；只能使用宿主保存的验证记录 |
| 只走放弃路径但未覆盖正常动作 | 覆盖不足，不标记可玩 |
| 计划/宏无等待循环或指数展开 | 静态拒绝或有界超时，不占满 API 进程 |
| 对手牌在错误/事件/选项中出现 | 视角测试失败，不发布 |
| 机器人错误、写库错误或中途重启 | 已提交 revision 保持一致，无半步成功 |
| 模型调用未经授权的确认/注册入口 | 宿主拒绝；验证通过不等于用户已核对 |

### 8.3 真实生成基准

- 保留 8 个已知族的现有回归，但与“陌生组合成功率”分开统计。
- 开发集为以上 3 个组合；盲测为机制冻结后新增 8 条可表达组合，另加至少 2 条缺机制反例。
- G2 初始准出目标：开发集 3/3 全链路完成；盲测至少 6/8 成功；2/2 反例正确拒绝；所有已注册产物均有当前有效验证凭据；已知错误被标可玩数量为 0。
- 分母包含所有事先判定可表达的请求；模型误报 unsupported、超预算和人工修 Plan 都算生成失败，不能从统计中移除。
- 统计 `known_parameterized / composed_generated / missing_feature / verification_inconclusive / generation_failed`，不把改标题或轮数当作新的机制组合成功。
- “所需机制都存在”“该 IR 可编译”“生成并验证通过”“浏览器真正可玩”四个指标分开；原来的 27/31 标签覆盖不能称为陌生生成成功率。
- 对支持范围的诚实修正可能降低覆盖率。用 ADR 说明与回归反例支撑，不能为维持“只升不降”的数字继续保留错误覆盖声明。

## 9. 真实运行验收与证据归档

本阶段为代码/运行时/UI 开发，单测和 mock 只能补充。每个影响链路的交付包必须从对应源码 checkout 启动真实应用。

### 9.1 现有可用命令

以下在将实施 G2 的 checkout 中运行；数据目录为验收专用目录，不复用用户真实对局。

```powershell
uv sync --frozen
npm ci --prefix frontend
npm run build --prefix frontend
$env:POCKER_AGENT_DATA_DIR = Join-Path (Get-Location) 'artifacts/g2-runtime'
uv run python scripts/run_web.py --skip-build --port 8012
```

另一个终端使用启动输出中的实际端口：

```powershell
uv run python scripts/doctor.py --url http://127.0.0.1:8012
uv run python scripts/e2e_smoke.py http://127.0.0.1:8012
```

窄范围测试按模块逐条运行；发布前再运行完整 `uv run pytest -q`。不要并行启动多套长耗时验证占用用户环境。

### 9.2 待实现的验收工具

- 扩展 `scripts/benchmark_generation.py` 的真实模型模式，读取组合用例和独立需求预期，而非只从 expect kind 选 `IR_TEMPLATES`。
- 增加 G2 HTTP E2E：描述/澄清 → 草案 → 正式验证 → 规则确认 → 注册 → 对局结束 → 重启恢复。
- 增加浏览器交互验收：文本输入、完整规则核对、多牌区选牌、机器人推进、结果、冲突反馈、移动导航与恢复。
- 诊断脚本检查解释器实际导入的包路径、后端 code fingerprint、前端 bundle，防止新页面连接旧服务。

上述脚本、组合测试文件和目标 API 在本基线尚不存在；实施时在对应 PR 增加，不能把这些名称作为已通过的命令记录。

### 9.3 每次记录必须包含

`git rev-parse HEAD`、dirty 状态、准确启动命令、Python/Node 版本、解释器与导入包实际路径、锁文件/前端构建来源、后端 code fingerprint、实际端口、数据目录、场景、步骤、预期与实测结果。

真实模型记录 provider/model、提示版本、预算与实际使用量；不记录 API Key。固定 session seed 与输入日志；不要求云端模型生成结果本身逐字节可重现。

归档目录建议 `artifacts/g2/<revision>/<run-id>/`，包含脱敏验证报告、规则与产物哈希、失败路径、浏览器截图/日志和运行摘要。报告引用完整服务器轨迹，不能以 view 最近 100 条事件冒充整局。

如果模型未配置、服务无法启动或浏览器不可操作，明确标为阻塞/未验证；不能用 scripted 模型或 HTTP-only 测试替代真实生成及浏览器验收。

## 10. 工作拆分与完成定义

### 10.1 建议首批 PR

1. **PR-A：能力事实与 ADR**。冻结基线、G2 子集、规范变更和独立场景预期。
2. **PR-B：操作与动作 Schema**。补强输入/输出/配置类型，区分绑定 ID，不引入 Agent 发布能力。
3. **PR-C：牌区与匹配职责拆分**。完成移牌、计分、结束解耦，旧调用迁移并删除重复行为。
4. **PR-D：ComposedRulesIR 及场景 A 编译切片**。只按机制降层；产物可模拟但未验证前不可发布。
5. **PR-E：验证服务和版本凭据**。完成当前 artifact 的正式门槛，再进入 Agent 与前端扩展。

每个 PR 可再拆为 ≤400 行的子 PR；按接口依赖顺序合入。不能为了行数把一个运行时切换拆成长期双路径，也不能借“必须删除”任意删掉仍在使用的能力。
