# Pocker Agent v0.4 前端与 UI 设计规范

> 面向：UI 设计师、交互设计师、前端工程师
> 版本：v0.4
> 目标：为规则驱动、可扩展的纸牌玩法平台建立统一的产品界面语言。

## 1. 产品定位

Pocker Agent 不是某一个固定纸牌游戏，而是一个把自然语言规则转化为可验证、可试玩游戏的工作台。前端应围绕“规则确认 → 能力验证 → 游戏运行 → 回放与诊断”设计，不为斗地主、21 点等单个玩法写专属页面。

前端只展示后端提供的规则、状态、合法动作和事件。前端不得自行实现胜负、牌型、计分或回合推进逻辑。

## 2. 用户主流程

```text
描述玩法 → 查看 RulesIR → 修订规则 → 检查能力
→ 生成/组装计划 → Playtest → 开始试玩 → 回放/诊断
```

任何阶段失败都要给出可理解的原因。无法表达的玩法显示 `unsupported`、缺失能力和下一步建议，不显示一个规则被悄悄简化后的“可玩版本”。

## 3. 信息架构

### 3.1 App Shell

- 顶部：产品标识、当前玩法名称、运行状态、返回入口。
- 左侧导航：玩法库、新建玩法、验证记录、设置。
- 主区域：当前页面内容。
- 全局通知：只用于成功、失败、需要用户处理的状态变化。

### 3.2 页面清单

| 页面 | 目的 | 主要用户动作 |
|---|---|---|
| 玩法库 | 查看已创建和最近试玩的玩法 | 打开、复制、删除、继续验证 |
| 新建玩法 | 输入自然语言需求 | 描述玩法、提交生成 |
| 规则确认 | 核对结构化 RulesIR | 修改规则、确认规则 |
| 能力检查 | 判断当前内核是否支持 | 查看缺失 axis、返回修改 |
| 计划验证 | 查看静态检查和 playtest | 运行验证、修复、重新验证 |
| 游戏工作台 | 真实试玩 | 选择合法动作、查看状态 |
| 回放与诊断 | 重放事件、定位错误 | 拖动时间线、查看状态差异 |

## 4. 新建玩法与规则确认

### 新建玩法

页面由三部分组成：

1. 玩法描述输入框：支持自然语言，多行输入；
2. 示例提示：展示“玩家数、牌堆、回合、动作、胜负、计分”等需要说明的内容；
3. 生成按钮：生成 RulesIR 草案。

生成中显示阶段进度：解析规则、检查缺口、准备确认。不要显示模型内部思考内容。

### 规则确认

RulesIR 以分组卡片展示：

- 基本信息：名称、玩家数量、队伍；
- 牌堆与区域：牌、数量、可见性；
- 发牌与回合：顺序、起始玩家、跳过规则；
- 动作：动作名称、触发条件、选择范围、效果；
- 胜负与计分：结束条件、赢家、分数变化。

每个字段都应显示“来源于用户描述”或“由系统推断”。推断字段必须允许编辑。保存前显示未填写项和潜在歧义。

## 5. 能力检查与验证页面

能力检查页的核心不是技术日志，而是回答三个问题：

- 当前规则能否表达？
- 哪些能力已经覆盖？
- 缺少什么，补上后能解决哪类问题？

状态分为：

- `可表达`：可以进入计划生成；
- `需组装`：需要生成 Macro 并经过验证；
- `unsupported`：当前协议无法表达。

错误卡片必须包含：能力名称、用户能理解的原因、影响的规则段、建议动作。禁止只显示异常堆栈。

## 6. 游戏工作台

### 6.1 布局

桌面端采用三栏布局：

```text
左栏：玩家、队伍、分数、可见信息
中栏：牌桌、牌区、公共区域、当前提示
右栏：规则摘要、状态检查、事件详情
底栏：合法动作、确认/取消、事件时间线
```

窄屏时变为：牌桌 → 合法动作 → 玩家信息 → 规则与事件抽屉。

### 6.2 通用牌桌

牌桌由后端 `view()` 返回的 zones、players、turn、legal_actions 和 events 渲染。前端只识别通用字段：

```json
{
  "zones": [],
  "players": [],
  "legal_actions": [],
  "turn": {},
  "scores": {},
  "phase": {},
  "finished": false,
  "events": []
}
```

牌区支持：手牌、公共牌、牌堆、弃牌区、目标区、隐藏区。每个区域应有明确标题、数量和可见性提示。

### 6.3 合法动作

动作栏只渲染后端返回的 `legal_actions`。动作至少包含 id、label、参数 schema、是否需要选牌/选人。不可用动作不应伪装成可点击按钮；若需要展示，必须说明禁用原因。

提交动作时携带 `session_id`、`revision` 和动作参数。版本冲突时提示“局面已更新，请刷新当前状态”，不得覆盖新状态。

### 6.4 状态与反馈

- 当前回合：高亮当前玩家和待处理区域；
- 动作成功：牌移动、分数变化、事件提示同步出现；
- 动作失败：保留用户选择，显示具体校验原因；
- 终局：显示赢家、结算、重新开始、查看回放；
- `unsupported`：显示在规则/验证区域，不进入试玩页面。

## 7. 事件与回放

事件是表现层唯一接口。事件时间线支持：发牌、移动、揭示、动作、计分、回合变化、终局和错误。

每个事件显示时间、事件类型、参与者和简短描述。点击事件可查看前后状态差异。回放必须支持暂停、逐步前进、跳转到终局和从某个 revision 复制局面。

## 8. 视觉语言

- 风格：克制、清晰、偏桌面工作台，不使用赌场式装饰；
- 颜色：中性色为基础，使用单一强调色标记当前回合和主要动作；
- 状态色：成功、警告、错误、不可支持必须有颜色加文字双重表达；
- 动效：只表现状态变化和牌移动，默认短、快、可关闭；
- 字体：优先保证数字、牌面符号和中文可读性；
- 卡片：用于分组信息，不要把每一条事件都做成浮层。

## 9. 前端组件边界

建议组件：`AppShell`、`GameWorkspace`、`ZoneView`、`CardView`、`PlayerPanel`、`ActionBar`、`RuleInspector`、`CapabilityReport`、`PlaytestReport`、`EventTimeline`、`ReplayControls`。

组件不得包含玩法专属判断，例如 `isDoudizhuBomb`、`blackjackTotal`。如需展示特殊牌型，应由后端事件或通用 pattern 描述提供文案。

## 10. 交互状态与错误文案

所有异步操作至少覆盖：空闲、加载、成功、失败、重试、冲突、不可支持、已结束。错误文案使用“发生了什么 + 为什么 + 下一步能做什么”的格式。

示例：

> 当前规则需要“按玩家视角抽取隐藏牌”，内核暂不支持。你可以修改规则，或等待信息集能力加入后重新检查。

## 11. 验收标准

- 同一套工作台可以加载 arithmetic、shedding 等不同玩法；
- 页面不依赖具体玩法名称来决定布局或动作；
- 合法动作完全来自后端；
- revision 冲突不会覆盖新状态；
- 能展示 `unsupported` 和缺失能力；
- playtest 失败时可以定位到规则、计划或事件；
- 刷新页面后可以恢复 session 和当前局面；
- 回放与实时事件使用同一套事件模型；
- 桌面和窄屏布局均可完成一次完整试玩。

## 12. 设计交付物

UI 设计阶段应交付：

1. App Shell 和六个核心页面的高保真稿；
2. 桌面、平板、窄屏三个断点；
3. 牌区、手牌、动作栏、状态卡、错误卡、事件时间线组件规范；
4. 加载、空状态、失败、unsupported、终局等状态稿；
5. 设计 token：颜色、字体、间距、圆角、阴影、动效时长；
6. 与前端对应的组件命名和交互说明；
7. 一套 arithmetic 和一套 shedding 的真实数据示例。

## 13. 实施顺序

先完成静态 App Shell、规则确认页和通用 GameWorkspace，再接入 arithmetic Session，随后接入第二种玩法验证通用性。只有在两种不同结构的玩法都能使用同一套页面后，才开始补充隐藏信息、触发器和复杂牌型的专用表现。
